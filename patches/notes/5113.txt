5113 ole32: file moniker ParseDisplayName and anti-moniker GetDisplayName with a left moniker (gap-CORE items 460 FileMonikerImpl_ParseDisplayName, 461 AntiMonikerImpl_GetDisplayName).
FileMoniker::ParseDisplayName (E_NOTIMPL, which made MkParseDisplayName fail on any "file!item" name once the file part was parsed) now binds the moniker to the object behind the file (through the running object table, else the file's class: IMoniker::BindToObject with IID_IParseDisplayName) and lets that object parse the rest, as the class moniker (classmoniker.c) and the item moniker do; its result and the characters eaten are the object's. E_POINTER for NULL out pointers, *ppmkOut / *pchEaten cleared first, a failed bind gives its own error.
AntiMoniker::GetDisplayName ignores pmkToLeft: its name is one "\.." per level whatever is to its left (it answered E_NOTIMPL for a non-NULL one, which also broke composites asking each part with its left neighbour).
Docs: learn.microsoft.com/en-us/windows/win32/api/objidl/nf-objidl-imoniker-parsedisplayname (reads as much of the display name as it understands and makes a moniker of it; pmkToLeft is the moniker to the left in a composite) and nf-objidl-imoniker-getdisplayname (pmkToLeft is mainly for the implementer's cooperation between the parts of a composite).
Unverified: that Windows' file moniker parses through IParseDisplayName of the bound object (the code mirrors ClassMoniker_ParseDisplayName, whose tests ran on Windows); that an anti-moniker really ignores its left neighbour on Windows (no test; the old E_NOTIMPL came with a FIXME rather than a test).
