5202 gdi32: GetCharacterPlacementW fills GCP_RESULTS.lpClass (gap-CORE 223); include/wingdi.h GCPCLASS_* values.
Docs: learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-gcp_resultsw (lpClass: ARABIC, HEBREW, LATIN, LATINNUMBER, LOCALNUMBER on output; with GCP_CLASSIN the nonzero entries are kept and only zero ones computed) and nf-wingdi-getcharacterplacementw.
Bug fixed on the way: Wine's wingdi.h had GCPCLASS_ARABIC 3, NEUTRAL 4, LOCALNUMBER 5 ... where the Windows SDK values (mingw-w64's wingdi.h, which is freely licensed) are ARABIC 2 (same as HEBREW), NEUTRAL 3, LOCALNUMBER 4, LATINNUMBER 5, LATINNUMERICTERMINATOR 6, LATINNUMERICSEPARATOR 7, NUMERICSEPARATOR 8. Programs built for Windows pass those numbers. Nothing else in the tree used the old values.
Classification is by Unicode block (Hebrew 0590-05FF and FB1D-FB4F, Arabic 0600-06FF 0750-077F FB50-FDFF FE70-FEFF, Arabic-Indic digits 0660-0669 06F0-06F9 are local numbers, ASCII digits Latin numbers, everything else Latin). Unverified: Windows' class for neutral characters between RTL text and for digits next to RTL text (the docs list NEUTRAL, the separators and terminators as input-only), and the 'only LATIN is meaningful without GCP_REORDER' remark is not applied. The text is not reordered by class; GCP_REORDER keeps using the existing bidi code.
