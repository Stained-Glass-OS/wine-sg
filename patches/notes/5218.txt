5218 win32u: ETO_NUMERICSLOCAL / ETO_NUMERICSLATIN in ExtTextOut (gap-CORE 717).
Docs: learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-exttextoutw ("ETO_NUMERICSLATIN: to display numbers, use European digits. ETO_NUMERICSLOCAL: to display numbers, use digits appropriate to the locale").
NtGdiExtTextOutW only logged a FIXME. It now draws a copy of the string: with ETO_NUMERICSLOCAL the digits 0-9 become the user locale's digits (LOCALE_SNATIVEDIGITS: the user override HKCU\Control Panel\International\sNativeDigits, else the locale's value from the NLS data; for en-US that is 0-9, so nothing changes), with ETO_NUMERICSLATIN the Arabic-Indic (U+0660..0669), Extended Arabic-Indic (U+06F0..06F9) and the locale's own native digits become 0-9. Glyph-index text (ETO_GLYPH_INDEX) is not touched. win32u gets a pointer to the NLS string table (nls_locale_strings, set where get_locale_data loads the table) to read the native digits.
Unverified: "the locale" is taken as the user default locale, not the text's language or the DC font's charset (native GDI may apply local digits only in an Arabic/Hebrew context); LATIN converts the two Arabic digit ranges and the user locale's own digits, not every script's digits (Devanagari, Thai ... with a non-Latin user locale are converted only because they are that locale's native digits); the gate cannot run a non-Latin user locale (the user override stands in for it).
