5105 ntdll: XPRESS and XPRESS_HUFF compression (gap-CORE items 360 RtlGetCompressionWorkSpaceSize, 361 RtlCompressBuffer, 362 decompress). Both formats failed with STATUS_UNSUPPORTED_COMPRESSION and logged FIXMEs; LZNT1 already worked.
From the open specification [MS-XCA] (learn.microsoft.com/en-us/openspecs/windows_protocols/ms-xca; Microsoft's Open Specifications notice allows implementing it): COMPRESSION_FORMAT_XPRESS is "Plain LZ77" (32-bit flag words, 13-bit distance + 3-bit length, nibble/byte/word/dword length extensions) and COMPRESSION_FORMAT_XPRESS_HUFF is "LZ77+Huffman" (64K blocks, 256-byte table of 512 four-bit code lengths, 16-bit bit words interleaved with length bytes, end symbol 256). Decompressors follow the spec's pseudo-code; the Plain compressor follows its pseudo-code (so its output equals the spec's examples byte for byte); the Huffman compressor builds length-limited canonical codes (15 bits, a complete code always) with a hash-chain matcher. RtlDecompressFragment on these formats decompresses the whole stream and cuts the fragment. The workspace sizes are 16 / 0x1000 as for LZNT1 (the compressor keeps its tables in its own memory). The "semi-stub" FIXMEs of RtlGetCompressionWorkSpaceSize and RtlCompressBuffer become TRACEs; an unknown format is a WARN.
Unverified: the Rtl* wrappers' use of UncompressedChunkSize with these formats is not documented (docs: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-rtlcompressbuffer), so the chunk size is ignored and the buffer is one whole stream, which is also how the MS-XCA examples are given; the Huffman encoder's choice of codes and matches is its own (valid, decodes with the spec's decoder, not byte-identical to Windows); COMPRESSION_ENGINE_MAXIMUM only deepens the match search; the engine value is not validated; the decoder accepts a stream whose last symbol is not followed by an end symbol when the input runs out.
