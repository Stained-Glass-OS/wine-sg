6083 explorer, user32 (depth pass, main 2026-10-23: "if DOSBox's taskbar button or Alt+Tab entry really shows no icon, fix it"). Screenshots on the SG shell desktop showed: Alt+Tab switcher cards had no program icon for any program (Notepad++, DOSBox); DOSBox's console ("DOSBox Status Window", conhost.exe) taskbar button had no icon at all; explorer logged "NtUserDrawIconEx Error retrieving icon frame 0". Causes: (1) vdesktop.c's window_icon() and the switcher drew GetClassLongPtr/WM_GETICON handles of other processes -- Wine's HICONs are per process, so nothing is drawn; now a foreign window's icon is its program file's (QueryFullProcessImageNameW + ExtractIconExW, cached per file, 64 entries round-robin), as systray.c's taskbar buttons already did (exe_icon). Own-process windows (SgLinuxWindow stand-ins) keep their class/WM_GETICON icon. (2) user32 PrivateExtractIconExW, nIcons==1 with both pointers: HICON hIcon[2] was uninitialised and copied out even when ICO_ExtractIconExW extracted nothing (conhost.exe has no icon resources), so the taskbar's exe_icon was a stack value (seen: 0x7ffffeac86b0) and the IDI_APPLICATION fallback never ran; now NULL unless something was extracted (ret not 0 / ~0). The console button now shows the generic program icon (Windows shows the console program's icon -- a later refinement: map the conhost window to its client process).
Not done: cross-process HICON drawing in general (win32u keeps icon bits in the owner; thumbnail-toolbar button icons and overlay icons from ITaskbarList3 in another process are still drawn from foreign handles).
Gate: test-iconcross (ExtractIconExW on conhost.exe with a dirtied stack; a red-icon program's Alt+Tab card on a shell desktop, its caption without a system menu so only the shell draws red). Mutants SG_MUTANT_SWITCHER_FOREIGN_ICON (explorer), SG_MUTANT_EXTICON_GARBAGE (user32) caught.
