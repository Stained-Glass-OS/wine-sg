CORE review: setupapi / cfgmgr32 (CM_Request_Device_Eject is the only function that changes). Docs: learn.microsoft.com CM_Request_Device_Eject ("prepares a local device instance for safe removal, if the device is removable; if the device can be physically ejected, it will be"; pVetoType/pszVetoName describe a failure; flags not used; SeUndockPrivilege / SeLoadDriverPrivilege in some cases), PNP_VETO_TYPE.
Behaviour: unknown device node or the root of the tree: CR_INVALID_DEVNODE; flags != 0: CR_INVALID_FLAG; a name buffer of 0 characters: CR_INVALID_POINTER (GUESS: the codes); the veto type is set to PNP_VetoTypeUnknown and the name emptied first; a not-yet-registered (phantom) device node: CR_NO_SUCH_DEVNODE. The device's Capabilities (SPDRP_CAPABILITIES, a DWORD of CM_DEVCAP_*) must have CM_DEVCAP_EJECTSUPPORTED or CM_DEVCAP_REMOVABLE, else CR_REMOVE_VETOED with PNP_VetoNonDisableable and the instance id as the name (GUESS: the type). A device of the CD-ROM class: the active GUID_DEVINTERFACE_CDROM interface is opened and gets IOCTL_STORAGE_EJECT_MEDIA, which Wine's ntdll turns into the eject of the unix drive the prefix maps (nothing happens to hardware the prefix has no drive for); no interface -> CR_REMOVE_VETOED / PNP_VetoDevice; cannot open -> PNP_VetoOutstandingOpen (sharing violation) or PNP_VetoDevice; the ioctl refused -> PNP_VetoInsufficientRights (access denied) or PNP_VetoDevice. Any other removable device -> CR_SUCCESS: Wine's PnP manager has nothing to stop or unplug here (GUESS: Windows would stop the device and remove its subtree). Not done: the privilege checks; the _Ex variants (not exported); the A version converts the veto name.
