5205 user32/win32u: GetWindowDpiHostingBehavior (gap-CORE 624).
Docs: learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowdpihostingbehavior ("A window's hosting behavior is the hosting behavior of the thread in which the window was created, as set by a call to SetThreadDpiHostingBehavior. This is a permanent value and cannot be changed after the window is created, even if the thread's hosting behavior is changed").
SetThreadDpiHostingBehavior (patch 2208 keeps the per-thread value in a user32 TLS slot, untouched) now also writes it to a new field of ntuser_thread_info; win32u copies it into the window (WIN_DPI_MIXED_HOSTING in the window flags) when the window is created, before WM_NCCREATE, so the window procedure already sees it. GetWindowDpiHostingBehavior asks win32u through a new NtUserCallHwnd code. A bad window handle gives DPI_HOSTING_BEHAVIOR_INVALID (-1) with ERROR_INVALID_WINDOW_HANDLE; windows of other processes read as DEFAULT.
Unverified: the error value for a bad handle (the docs name none), the result for another process's window (their flags are not visible; always DEFAULT), and that nothing else in Wine honors the MIXED behavior (child windows of other DPI awareness are not treated differently).
Gate test/user32-dpihosting-gate.sh (64/32 bit); mutants DPIHOST_STUB and DPIHOST_LIVE (returns the calling thread's current behavior instead of the creation-time one) shown failing it.
