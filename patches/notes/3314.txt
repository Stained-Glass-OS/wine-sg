3314 rpcrt4: PointerUnmarshall gaps: FC_ALLOCATE_ALL_NODES and the freeing of the data of an FC_OP pointer (DECISIONS-2 RPC-NDR). Builds on 3313.
Implements: [allocate(all_nodes)] pointers (not through FC_POINTER_DEREF, and not a client over a pointer that has data): the referent tree is sized with the type's NdrMemorySizer pass on the buffer, one block (twice that plus 128 bytes, zeroed, from the stub's allocator) is allocated and NdrAllocate carves the nodes from it through pStubMsg->pAllocAllNodesContext (the first node, the root, is the block's start); PointerFree frees only that block for such a pointer. FC_OP: in a client the old referent of the pointer (and what it points to, with the type's free routine, unless it is in the buffer) is freed before the new data replaces it (FC_IP referents are skipped: their unmarshaller releases them; FC_POINTER_DEREF pointers are left as they were).
Unverified / guesses: the block size is an over-estimate (the memory-size pass may count less than the nodes take, then a node is allocated alone and the one-free property is lost for it: leak, no crash); no ground truth of Windows exists for either case (the Wine comment says an object pointer's data is freed before it is overwritten; the all_nodes rule is the MIDL documentation's "one allocation, one free"); widl has no [allocate] type attribute, so the gate calls NdrPointerUnmarshall/NdrPointerFree directly on hand-made formats (a list of complex structures of three nodes) instead of a client and server in two processes; if the unmarshaller raises an exception the context block is not freed.
Gate test/rpcrt4-ptrgap-gate.sh (64+32): a three node list is unmarshalled with plain pointers (3 allocations, 3 frees) and with all_nodes (1 and 1, the first node is the block), an FC_OP pointer in a client frees its old data (the freed pointer is the old one), in a server it does not, none when the pointer had no data.
Mutants shown caught: PTRGAP_NOOPFREE, NOALLNODES, FREENODES.
