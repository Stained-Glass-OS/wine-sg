5217 win32u: ActivateKeyboardLayout with an aliased layout (gap-CORE 699).
Docs: learn.microsoft.com/en-us/windows/win32/winmsg/wm-inputlangchange ("wParam: the character set of the new locale"), ActivateKeyboardLayout; an HKL's high word is the layout (0xf000 | layout id for the other layouts of a language, 0xe000 for IMEs), its low word the input language.
NtUserActivateKeyboardLayout logged "Aliased keyboard layout not yet implemented" and sent WM_INPUTLANGCHANGE with character set 0 for those. It now takes the character set from the input language (low word) when the high word is aliased, as for a plain layout from the high word. While there: every locale of Wine's NLS data has the ANSI code page CP_UTF8, so plain layouts also got character set 254 (PC437) instead of the ANSI one; a UTF-8 locale now uses the process's ANSI code page (the way get_input_codepage already does).
Unverified: the mapping of an aliased layout to its language is the HKL's low word, not a lookup of the layout id in HKLM\...\Keyboard Layouts; the gate only runs under the en-US user locale (a locale that is not the default can not be activated), so the character set it sees is the ANSI one of the process's code page.
