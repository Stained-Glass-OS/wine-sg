7824 server: the NSS questions of a shared prefix (connecting account a member of the prefix's group: uid_in_group; administrator: sg_uid_is_admin, 7737) are asked on a thread of their own (server/nssworker.c, reentrant getpwuid_r/getgrnam_r/getgrouplist, all signals blocked), answers handed back through a pipe the main loop polls. Each answer is computed exactly as before and afresh per question: no cache, nothing kept between questions (a removed administrator is not counted once asked again).
- Connection: accept -> root/owner/SO_PEERGROUPS admitted at once; otherwise, and for every account but root and the prefix owner, the lookup is queued; the process is created (token with that answer, via sg_connect_admin) or the connection refused when it comes. Fallback: asked synchronously if the thread cannot be started.
- Requests create_linked_token (full token), get_session_user_token, logon_ticket_token: STATUS_PENDING while asked; the answer is stored on the requesting thread and used once by its retry (ntdll TokenLinkedToken, advapi32 logon ticket, wtsapi32 WTSQueryUserToken loop every 20 ms). logon_ticket_token keeps the broker's ticket until the answer is there.
Why: with nsswitch "files winbind" (domain-joined machines), getgrouplist asks winbindd, which can take minutes waiting on a domain controller; on the main loop that stopped every Windows program of every account and made the server ignore SIGTERM. Found while chasing the iso-test privacy-page hang (not its cause there: winbindd is not running at first boot). Elevation model unchanged (main/David: no cache, same answer).
No protocol bump: no request structures changed; an old server never returns STATUS_PENDING.
Gate test-nssslow: two accounts in a user namespace on a shared prefix, LD_PRELOAD shim makes wineserver's lookups take 6 s each: first account's worst round trip during the second's connection < 2 s (got ~20-50 ms), second account waits ~12 s and runs with elevation Default. Mutant NSS_ON_MAIN_LOOP caught (12003 ms). splittoken, runasuser, wtstoken, renamesafe, sessgrow pass. The NSS admission path itself (account in the group per NSS but not in its credentials) is not reachable in the gate: the server directory's permissions stop such an account first.
