6046 winex11 (main, qa4 2026-10-22: Dropbox "white after lock" = two Chromium apps at once). Opera and Dropbox turn white, frames included, on lock/unlock or when another app starts.
Host reproduction: weston --backend=headless --xwayland, the Wine desktop, Opera 137 (autostart), sg-deskcomp started after Opera's window was up. Opera's whole window composited white; its GPU child X window still held the page (xwd of the child: #F4F2E4, of the top-level: #FFFFFF). Electron 30 (child-window path) stayed fine; with deskcomp started first, Opera stayed fine.
Cause:
- Opera's GPU process renders into Opera's top-level through 0586's top case (a client X window inside the browser's X window). The top-level has child HWNDs, so needs_offscreen_rendering made the surface offscreen: the client window was manually redirected, and each present was copied into the browser's X window.
- Any later flush of the browser's window surface (an expose from deskcomp's redirect, a lock, a focus change, another app causing a repaint) painted over the copy.
- 1523's reshow (vulkan_surfaces_reshow from the window surface flush) runs in the process that flushes: the browser, which has no shown surfaces. The GPU process, which keeps the frame, never learns of the flush. A still page presents nothing more, so it stayed white.
Fix: vulkan_surface_update_offscreen keeps a surface of another process's top-level non-offscreen (foreign_toplevel: parent is the desktop, owner pid differs) unless it is a glass/blend surface or a DPI scale needs the copy. The client window inside the browser's X window is then shown in place, and X keeps the browser's painting out of it (ClipByChildren), as Windows' DWM keeps a swap chain over GDI. A TRACE "offscreen N" was added on changes.
Verification:
- On the host repro, Opera stays rendered with deskcomp started late (e0c1/e1c1/e1c0 matrix: Opera #F4F2E4, Electron #FF0000), and the screenshot is correct (frame, tabs, page).
- Gate xproc-still (test-xproc-still; Xvfb + DXVK): a render process presents into a host top-level that has a child window, then the host repaints. The gate checks from the +vulkan trace that the surface never went offscreen. A pixel check was tried and dropped: neither Xvfb nor a headless Xwayland showed this probe's Vulkan frames, in either mode, while real Opera's did. The visual check is the Opera run above.
Mutant caught: SG_MUTANT_VK_FOREIGN_OFFSCREEN (1 FAIL).
Regression: gates xproc-vk, vkchild and glasspixel pass. glassvk and layeredblend fail the same way with and without this patch (desktop backdrop expectations of the dev tree's prefix), so not a regression.
Not covered: another process's child window (0586's child case) is still offscreen + copy (Electron with frames). It did not go white in the repro, but a browser repaint can wipe it the same way; a cross-process reshow would need the GPU process to learn of the browser's flushes.
