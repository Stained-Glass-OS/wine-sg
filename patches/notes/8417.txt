8417 dlls/win32u/font.c update_external_font_keys -- apps9, batch K (Scilab 2027 on qa5 drew its menus and panel titles as boxes).
Cause: Java's runtime on Windows takes Dialog from ARIAL.TTF (7711 links arial.ttf to whatever font "Liberation Sans (TrueType)" names in HKLM Fonts). qa5's machine prefix had no Liberation Sans/Serif/Mono entries in HKLM Fonts, while both users' HKCU\Software\Wine\Fonts\External Fonts still had them. So win32u took them as listed (ADDFONT_EXTERNAL_FOUND) and never wrote them again. 7711's clean-up then dropped the arial/times/cour links whose targets were no longer registered. A fresh prefix on qa5 has them all. The entries were taken by an uninstaller that shipped the same fonts: LibreOffice's MSI writes and removes "Liberation Sans (TrueType)" (it was walked on qa5).
Fix: in the record pass, a remembered face whose file still matches is FOUND only if the Fonts key still has its value (NtQueryValueKey, KeyValueBasicInformation, STATUS_OBJECT_NAME_NOT_FOUND). Otherwise the write pass sets it again. A value an installer changed to its own file is left alone. A process that cannot open HKLM Fonts (winnt_key 0) behaves as before. This runs only at the first font start per user per wineserver (the volatile Cache key), so wineboot -u (run as the prefix owner, GDI init in process, 6533) heals the machine prefix and then relinks arial.ttf.
Gate fontrecord (test-fontrecord, Liberation on the host, else SKIP): a fresh prefix lists Liberation Sans and links arial.ttf; reg delete; the next program's font start writes it again; delete it and arial.ttf, then wineboot -u relinks arial.ttf; an installer's own value ("LiberationSans-Regular.ttf") survives a font start. Mutant SG_MUTANT_TRUST_EXTERNAL_RECORD.
