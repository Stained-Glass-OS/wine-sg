5114 rpcrt4: RpcMgmtSetComTimeout (gap-CORE item 554, a stub that answered success whatever it was given) and RpcMgmtInqComTimeout (an unimplemented @stub export, added so the value can be read back).
The client binding keeps a communications time-out hint, default RPC_C_BINDING_DEFAULT_TIMEOUT (5), copied by RpcBindingCopy. Set: 0..10 (RPC_C_BINDING_INFINITE_TIMEOUT), RPC_S_INVALID_TIMEOUT beyond, RPC_S_INVALID_BINDING for NULL, RPC_S_WRONG_KIND_OF_BINDING for a server binding. Inq: the same errors, an invalid argument for a NULL result pointer. Docs: learn.microsoft.com/en-us/windows/win32/api/rpcdce/nf-rpcdce-rpcmgmtsetcomtimeout: "Communications time-out value, from zero to 10. These values are not seconds ... Depending on the protocol sequence ... the time-out value acts only as a hint to the RPC run-time library ... ignored for ncalrpc"; return values RPC_S_OK, RPC_S_INVALID_BINDING, RPC_S_INVALID_TIMEOUT, RPC_S_WRONG_KIND_OF_BINDING.
Unverified: the hint is stored but no transport reads it yet (the docs say it is only a hint; for ncacn_ip_tcp it turns on keep-alives, which Wine's TCP transport does not do); the order of the checks when both the binding kind and the value are wrong; the public prototype of RpcMgmtInqComTimeout was left out of include/rpcdce.h to avoid rebuilding every user of that header (mingw's headers declare it).
