3313 rpcrt4: RpcMgmtSetCancelTimeout and the cancel timeout of RpcCancelThread, RpcCancelThreadEx and RpcAsyncCancelCall(FALSE) (DECISIONS-2 RPC-NDR). Builds on 3311; gate needs widl 3309.
Implements (MS docs for RpcMgmtSetCancelTimeout, RpcCancelThread, RpcCancelThreadEx): RpcMgmtSetCancelTimeout sets the timeout of the calling thread (default RPC_C_CANCEL_INFINITE_TIMEOUT); RpcCancelThread uses the target thread's timeout and RpcCancelThreadEx its own argument: 0 abandons the call now (RPC_S_CALL_CANCELLED), otherwise PKT_CO_CANCEL is sent and the call goes on until the server answers, or for that many seconds, when it is abandoned (RPC_S_CALL_CANCELLED for Ex, RPC_S_CALL_FAILED for RpcCancelThread as the docs say; the server's stub keeps running). RpcAsyncCancelCall(FALSE) applies the timeout of the calling thread: 0 abandons the call, a limit abandons it later (a timer; the call's end removes it), infinite waits. 
Unverified / guesses: the behaviour change that RpcCancelThread no longer abandons the call at once unless the thread's timeout is 0 follows the docs (before: always at once); a cancel when the thread is not inside a send/receive does nothing (no pending-cancel state); the PKT_CO_CANCEL is sent for ncalrpc and ncacn_np too (the docs say they need a finite timeout); a timeout of 0 sends no PDU; the status of a call abandoned by RpcMgmtSetCancelTimeout(0) + RpcAsyncCancelCall is RPC_S_CALL_CANCELLED.
Gate test/rpcrt4-canceltimeout-gate.sh: widl client and server in two processes (ncalrpc, ncacn_ip_tcp; 64+32): RpcCancelThreadEx 0/1/4 seconds against a manager that looks and one that does not, RpcCancelThread with the default, 1 and 0 second thread timeouts, async cancel with infinite, 1 and 0 seconds, a call that ended before its timer, binding usable afterwards.
Mutants shown caught: CANCELTO_ALWAYSNOW, NOPDU, NOTIMER, DEFAULT0, NOSTATUS, ASYNCINFINITE, NOASYNCTIMER.
