How: CDecodeMsg_StreamScan walks the BER headers of the bytes received so far (ContentInfo, then the path of the kind: data -> [0] -> OCTET STRING; signed -> SignedData -> version, digest algorithms, encapsulated content info -> [0] -> OCTET STRING; enveloped -> EnvelopedData -> version, recipients, encrypted content info with its algorithm -> [0] implicit string), restartable where a header is cut short, with a stack of up to 8 nested constructed strings, definite and indefinite lengths. Content octets are delivered as they arrive; the call that delivers the last one carries fFinal (an empty content: one call with 0 bytes; indefinite lengths: the end-of-contents makes a final call of 0 bytes). An update that fails (bad tag, callback fault or false) restores the scan state, the bytes and the message state, so the same update can be sent again. A signed message with no content in it, a detached message (CMSG_DETACHED_FLAG), hashed and other content types are not scanned: no callbacks, decode at the end as before. Typed (bare) messages start at their own structure.
Enveloped: the header is decoded as soon as the encrypted content info's algorithm has arrived (a synthetic EnvelopedData is built from the header pieces), so CMSG_ENVELOPE_ALGORITHM_PARAM (new: a CRYPT_ALGORITHM_IDENTIFIER, also for non-streamed messages), CMSG_RECIPIENT_COUNT_PARAM and CMSG_RECIPIENT_INFO_PARAM work; CMSG_CTRL_DECRYPT before the end imports the key now and decrypts what is queued and what follows through CryptDecrypt (a block cipher keeps its last block back until the end so the padding is stripped; the final call has the rest); after the end it decrypts as before and then hands the plain text to the callback in one final call. With a streamed key the plain text is only given through the callback (CMSG_CONTENT_PARAM stays empty). CMSG_CTRL_DECRYPT twice: CRYPT_E_ALREADY_DECRYPTED.
Before a streamed message ends CryptMsgGetParam fails with CRYPT_E_STREAM_MSG_NOT_READY (CMSG_TYPE_PARAM answers once the kind is known).
