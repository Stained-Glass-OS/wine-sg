5093 ntoskrnl: gap-CORE items 1143 (IoRegisterPlugPlayNotification) and 1144 (IoUnregisterPlugPlayNotification).
Docs: learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-ioregisterplugplaynotification (categories, PNPNOTIFY_DEVICE_INTERFACE_INCLUDE_EXISTING_INTERFACES, NotificationEntry, DRIVER_NOTIFICATION_CALLBACK_ROUTINE with the category's structure, the driver object is referenced while registered), nf-wdm-iounregisterplugplaynotification, ns-wdm-_device_interface_change_notification, ns-wdm-_target_device_removal_notification. The event GUIDs are the documented GUID_DEVICE_INTERFACE_ARRIVAL / _REMOVAL / GUID_TARGET_DEVICE_REMOVE_COMPLETE (values from mingw-w64's wdmguid.h).
Not as Windows: interface notifications are delivered in the process where IoSetDeviceInterfaceState runs (a driver in another winedevice process does not hear about interfaces another process enables later; the EXISTING pass does see them, it reads the registry); only the remove-complete event is sent for a target device (no query-remove or cancel, Wine's PnP manager does not ask), and the match is the registered file's device or anything below it in the removed device's stack; hardware profile registrations never fire (no profiles); no custom target events (IoReportTargetDeviceChange stays as it was); the callback runs on the thread that changes the state / removes the device, under the registration lock, so IoUnregisterPlugPlayNotification waits for a running callback; a callback must not unregister itself from another thread it waits for.
The callback typedef in ddk/ntddk.h returns VOID where Windows' returns NTSTATUS (left as it was).
