6026 ntdll (coordinator row, ImgBurn / Delphi programs): a 32-bit (WoW64) thread's stack overflow. The overflow exception of a 32-bit thread is first a 64-bit exception frame (KiUserExceptionDispatcher's CONTEXT, record and xstate, ~1.8 KB with AVX) on the thread's 32-bit stack, until Wow64PrepareForException moves it to the 64-bit stack; then the 32-bit frame and the program's own handlers run on what is left. is_inside_thread_stack gave a 32-bit stack one guaranteed page (upstream's value), so virtual_setup_exception found the frame past the last page and aborted the thread: a main thread's process exited 1, a secondary thread vanished while its process went on (or hung on a lock the thread held). Now a 32-bit stack keeps three pages for the exception (SetThreadStackGuarantee still raises it), and an exception that has no stack left to be dispatched on ends the process with STATUS_STACK_OVERFLOW, as Windows ends it, instead of the thread alone (64-bit too).
Docs: learn.microsoft.com "Thread Stack Size", SetThreadStackGuarantee, _resetstkoflw (a second overflow without the guard page ends the process).
Gate wowstack (test-wowstack), 64 and 32: endless recursion reaches the unhandled exception filter on the main thread and on another thread; a vectored handler with a 3000-byte frame sees STATUS_STACK_OVERFLOW on both; two threads overflow in turn; an unhandled overflow on another thread ends the process; a handler that overflows again ends the process (not just its thread). Before (dev tree at 10.0-489): 32-bit fails the two vectored-handler checks (exit 1, or the process goes on), a -O1 build fails all. Mutants caught: SG_MUTANT_WOWSTACK_ONE_PAGE (the two handler checks, 32-bit), SG_MUTANT_WOWSTACK_ABORT_THREAD (the second-overflow check, both).
Conformance vs before (macros = the old behaviour), 64/32: ntdll exception 4 = 4 / crash = crash (32-bit, pre-existing at exception 17, test_prot_fault), virtual 0 = 0, thread 0 = 0; kernel32 thread 0 / 1 = 1, virtual 684 = 684 / 692 = 692.
Left: 32-bit unhandled overflow with the debugger started (no SEM_NOGPFAULTERRORBOX) ends with an access violation in the debugger start-up, not STATUS_STACK_OVERFLOW.
