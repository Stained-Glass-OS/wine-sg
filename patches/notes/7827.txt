7827 winex11 sg_embed: lock order. The state thread (handle_wm_request) took embed_mutex while holding X's error lock (X11DRV_expect_error around each _NET_WM_STATE request it hears); the frames' thread takes embed_mutex and then the error lock for its X calls under it (sg_embed_layout, FocusIn/FocusOut, _GTK_FRAME_EXTENTS, attach's get_extents). With both at once explorer deadlocked: gdb on qa5 showed the main thread on error_mutex (winex11 +0x9dc20), the state thread on embed_mutex (+0x98a00). The shell gone, new Wine processes hung in start.exe (desktop owner dead), and a SgLinuxWindow frame whose X client had exited stayed mapped, full screen, over everything -- what looked like a frozen display after RDM's "Open (external)" multi-monitor session (sdl-freerdp3 /multimon: two full-screen windows passing the focus back and forth while asking for states). Very likely also David's 11-15 Enshrouded incident on 910 (full-screen Proton game exited, frame stayed with 0 children, shell hung, nothing started).
Fix: the state thread syncs and releases the error lock (X11DRV_check_error) before embed_mutex and expects again after; every other path already takes embed then error.
Gate test-embedlock: two framed windows, the X focus passed ~1000/s while both ask maximized on/off for 15 s; the shell answers (probe within 20 s), frames gone with the program, a new Windows program starts; then the same with window A full screen and the program ending mid-storm with its windows up: no frame or full-screen window of the shell's left, the pointer free. Mutant EMBED_LOCK_ORDER caught (probe no answer in 20 s, nothing starts). linuxembed, embedfs, embedconf, embeddragmax, embedmaxgrab, embedmenu, embedscale, embedselfsize, ownframe, embedmm pass.
