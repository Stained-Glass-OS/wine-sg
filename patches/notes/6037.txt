6037 msado15 (DB-ADO "Left": Recordset write-back). Connected recordsets never wrote anything: Update and UpdateBatch returned E_NOTIMPL after clearing the edit mode. Now each change is tracked per row (the values as read, kept at the first change; added rows marked) and written as ADO's client cursor writes it, through an internal Command with parameters on the recordset's connection:
- The table comes from the source: an adCmdTable name, or the single table of a SELECT (no joins).
- UPDATE <table> SET <changed columns> WHERE <key columns> AND <changed columns' old values>. This is ADO's default Update Criteria (adCriteriaUpdCols). The key comes from the provider's PRIMARY_KEYS schema (OpenSchema); with no key, every comparable column is used.
- AddNew + Update is an INSERT of the given columns. Delete is a DELETE by key (or all comparable columns).
- Immediate mode writes on Update and when moving off an edited row (Move*, AddNew).
- adLockBatchOptimistic keeps the changes, including deleted rows' values, until UpdateBatch. CancelBatch restores changed rows, drops added ones and brings back deleted ones.
- A statement that affects no row is DB_E_CONCURRENCYVIOLATION (0x80040E38).
- A sort moves each row's change record with it.
- Read-only recordsets write nothing.
Gate adoupdate (test-adoupdate; mock ODBC driver test/adomock-driver.c, whose SQLPrimaryKeysW now returns ODBC's six columns, all typed as strings). It checks: Update, the implicit update on a move, AddNew, Delete, batch pending/UpdateBatch/CancelBatch, a conflict with another writer, read-only, and the logged statements (key + changed-column criteria, INSERT values).
