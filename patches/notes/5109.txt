5109 ole32: StgOpenStorageEx (gap-CORE item 505, "Stub: calling StgOpenStorage, but ignoring pStgOptions and grfAttrs").
What was really wrong is that riid was ignored too: the IStorage pointer was stored in *ppObjectOpen whatever the caller asked for, so a request for IID_IPropertySetStorage handed out an IStorage and the next call went to the wrong method. It now asks the opened storage for riid (IID_IStorage, IID_IPropertySetStorage, IID_IUnknown; anything else is E_NOINTERFACE with *ppObjectOpen NULL), a NULL ppObjectOpen is STG_E_INVALIDPOINTER and a missing riid STG_E_INVALIDPARAMETER. pStgOptions and grfAttrs: the docs (learn.microsoft.com/en-us/windows/win32/api/coml2api/nf-coml2api-stgopenstorageex) say pStgOptions describes "the storage object opened" and only usVersion needs to be set, and grfAttrs may only be 0 or FILE_FLAG_NO_BUFFERING (still checked); neither changes how an existing compound file is read (the sector size is in the file), so ignoring them is correct and the FIXME becomes a comment.
Unverified: STGFMT_ANY and STGFMT_STORAGE still open a compound file only (an NTFS file's property sets need a different object); the exact HRESULT Windows gives for an unsupported riid.
Gate test/ole32-stgopenex-gate.sh (probe test/ole32-stgopenex-probe.c, 64+32 bit: a property set is written into a compound file, then opened through StgOpenStorageEx(IID_IPropertySetStorage) for the three formats and the property read back; IStorage, IUnknown, IStream, NULL pointer, missing file, STGFMT_FILE). Mutant STG_OPENEX_RIID (the old behaviour) fails it.
