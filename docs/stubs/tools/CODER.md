## Per batch (a batch = one coherent patch or a few small ones; push after EVERY batch)
1. BASELINE once per touched DLL before your first change: run the full suite of each touched DLL (suite.sh, both x86_64 and i386) on the unmodified base into /var/tmp/d7/<yourname>/base/.
2. Implement per the docs. Prefer standard Wine conventions (TRACE/WARN, unix-side calls only where needed, style of the surrounding code). Add Wine conformance tests to the DLL's tests/*.c that encode the documented Windows behaviour (tests must pass on both architectures; use todo_wine only for behaviour Wine really lacks). No code comments narrating the task; comments only for non-obvious Windows behaviour with the doc reference.
3. GATE with MUTANTS: each patch needs a test that fails when its logic is wrong. Mutants are `#ifdef SG_MUTANT_<NAME>` hooks in the patched code; show each failing by deleting the object files of that module and rebuilding with the define: PE-side code: `make x86_64_CFLAGS="-g -O2 -DSG_MUTANT_X" i386_CFLAGS="-g -O2 -DSG_MUTANT_X" dlls/<dll>/all`; unix-side code: `make CFLAGS="-g -O2 -DSG_MUTANT_X" dlls/<dll>/all`; then rebuild clean afterwards and re-check. Trust/validation/security checks need mutants that wrongly ACCEPT.
4. CONFORMANCE: after the batch run the full suites of every touched DLL (both arches) into /var/tmp/d7/<yourname>/b<N>/ and compare with the baseline using cmpsuite.py: zero NEW failures. Baseline failures that are network/environment related stay.
5. mkpatch.sh -> patches/sg/<NNNN>-<slug>.patch (numbers from your assigned range, ascending), patches/notes/<NNNN>.txt whose first line is "CORE: integrator must review" for core DLLs else "NOTE:"; the notes list the gate, the mutants shown failing, and every GUESS ("Unverified: ..."). If your patch needs another branch's patch applied first (it depends on code from fast-a/fast-b), say "applies after <branch> <NNNN>" in the notes.
6. Trademark rule: strings your patch adds never call the product "Windows" as a name (see CLAUDE.md-like rules in RULES.md: neutral wording or "Stained Glass"); paths, identifiers, comments are fine. New patch descriptions may say Windows in prose.

Every item of your group ends implemented or triaged with its OWN evidence; no bulk lines.
